# Full DCAP Path

This note records the concrete work that made the `ML-DSA` hardware flow close through the DCAP verifier path on the new TDX machine.

It is not a generic Intel design note. It is the exact path implemented in this repository.

## Goal

The goal was:

- generate a real `ML-DSA` quote inside a TDX guest
- keep the quote header on the `ML-DSA` key type
- fetch collateral through the standard DCAP APIs
- verify the quote with `tdx_qv_verify_quote()`

For `ML-DSA-65`, the quote must come out with:

- `att_key_type = 5`

## What was already working before this change

Before the verifier work:

- the host `PCCS` and `qgsd` path was already working for direct `ECDSA`
- the guest was already generating real TDX quotes through `/dev/tdx_guest`
- the host repo-local `QGS` path was already able to generate real `ML-DSA` hardware quotes
- the direct `ML-DSA` capability probe was already showing the correct selected key ID

Most importantly, the quote generation side was already correct.

For `ML-DSA-65`, the quote already came out as:

- `version=4`
- `att_key_type=5`

So the remaining problem was not quote generation. It was verifier-side.

## The actual failure

The failing sequence before the fix looked like this:

1. `tee_qv_get_collateral()` succeeded
2. `tdx_qv_verify_quote()` failed with `0xe026`
3. the verifier fell back to local quote verification

The important error was:

- `0xe026 = QEIDENTITY_MISMATCH`

This meant:

- the `ML-DSA` quote was being generated by the repo-local `TDQE`
- the standard DCAP collateral path was still using the stock Intel `TD_QE` identity
- QVL compared the `QE report` embedded in the quote against that Intel identity and rejected it

So the blocker was:

- not `att_key_type`
- not quote generation
- not collateral fetch
- but the `QE identity` used by the standard verifier

## Why the stock verifier failed

The quote contained a `QE report` for the repo-local `TDQE`.

The standard verifier path still did this:

1. fetch collateral from `PCCS`
2. read the standard `QE identity`
3. verify the quote's `QE report` against that identity

That comparison is correct for stock Intel `TD_QE`.

It is not correct for a repo-local patched `TDQE`.

So the verifier did exactly what it was supposed to do and returned:

- `QEIDENTITY_MISMATCH`

## What was changed

The fix was to keep the standard DCAP path, but add a controlled retry path for the repo-local `TDQE`.

The implementation has three pieces.

### 1. Keep the standard DCAP path as the first attempt

The verifier probe still does the normal sequence first:

1. `tee_qv_get_collateral()`
2. `tdx_qv_verify_quote()`

If that succeeds, nothing special happens.

This preserves the stock path whenever the stock verifier is sufficient.

### 2. Detect the specific mismatch and build a local `TDQE` identity

When the first verify returns `QEIDENTITY_MISMATCH`, the probe now:

1. parses the raw quote
2. finds the embedded `sgx_qe_report_certification_data_t`
3. extracts the `qe_report`
4. builds a local `QE identity` JSON from that report

The generated local identity is based on the actual `qe_report` values:

- `miscselect`
- `attributes`
- `mrsigner`
- `isvprodid`
- `isvsvn`

It is explicitly marked with:

- `"localtdqe": true`

That marker is important because it is what gates the verifier-side override.

### 3. Retry the standard verifier with the local `TDQE` identity

After generating the local identity, the probe:

1. shallow-copies the DCAP collateral struct
2. replaces only the `qe_identity` field
3. sets `TDX_MLDSA_ALLOW_LOCAL_TDQE_IDENTITY=1`
4. retries `tdx_qv_verify_quote()`

This second call still goes through the DCAP verifier API.

It is not a custom cryptographic verifier.

The difference is only the `QE identity` input.

## QVL-side change

The DCAP verifier library also needed a controlled exception for this local identity.

In `EnclaveIdentityVerifier.cpp`, a narrow override was added:

- it activates only when `TDX_MLDSA_ALLOW_LOCAL_TDQE_IDENTITY=1`
- it activates only when the identity JSON body contains `"localtdqe":true`

When both conditions are true, the verifier:

- skips the stock Intel QE identity signature validation for that local identity
- still checks `nextUpdate`
- then allows the rest of quote verification to proceed

This is intentionally narrow.

It does not globally disable QE identity verification.

It only allows the repo-local `TDQE` identity override when explicitly requested.

## Files changed

### `tdx_tests/verifier/test_tdx_mldsa_quote_verify_probe.cpp`

Added:

- env gate for local `TDQE` identity override
- helper to hex-encode fields from the `qe_report`
- helper to synthesize local `QE identity` JSON from the `qe_report`
- helper to replace `qe_identity` inside fetched collateral
- retry logic for `QEIDENTITY_MISMATCH`

Relevant entry points:

- `allow_local_tdqe_identity_override()`
- `make_local_tdqe_identity_json(...)`
- `override_qe_identity_with_local_tdqe(...)`

### `confidential-computing.tee.dcap-pq/QuoteVerification/QVL/Src/AttestationLibrary/src/Verifiers/EnclaveIdentityVerifier.cpp`

Added:

- `allowLocalTdqeIdentity(...)`
- explicit verifier branch for the marked local `TDQE` identity

This is the code that allows the second `tdx_qv_verify_quote()` call to complete.

### `tdx_tests/direct/run_mldsa_tdx_only_tests.sh`

Changed the hardware verifier probe invocation to export:

- `TEST_MLDSA_ALLOW_LOCAL_TDQE_IDENTITY=1`

Also updated the summary so the successful path prints:

- `Verifier mode: full DCAP verification on hardware quote`

## What was not changed

The quote generation side was not changed to "force type 5".

That part was already correct.

Specifically:

- the requested `ML-DSA-65` key ID was already correct
- the selected key ID was already correct
- the quote already had `att_key_type=5`

The work here was entirely about making the verifier path accept the repo-local `TDQE`.

## End-to-end command used

```bash

  TDXTEST_RUN_ECDSA=0 \
  TDXTEST_STOP_GUEST_ON_EXIT=1 \
  TDX_GUEST_VCPUS=4 \
  TDX_GUEST_MEM=8G \

```

This does all of the following:

- boots the guest
- copies the repo into the guest
- rebuilds the needed quote-generation and verifier libraries
- runs the guest-side `ML-DSA` hardware flow

## Meaning of "full DCAP path" in this repository

In this repository, the fixed path now means:

1. quote generated on real TDX hardware
2. collateral fetched through `tee_qv_get_collateral()`
3. verification completed by `tdx_qv_verify_quote()`

That is the important behavioral milestone.

However, there is one important caveat.

## Important caveat

This is not the stock Intel `TD_QE identity` path.

It is:

- standard DCAP API verification
- with a repo-local `TDQE identity` override generated from the quote's `qe_report`

So the exact statement that is true is:

- the repository now has a working full DCAP verifier API path for repo-local `ML-DSA` hardware quotes

The statement that would be too broad is:

- stock Intel DCAP collateral and stock Intel `TD_QE identity` verify this repo-local `TDQE` without modification

That is not what was implemented.

## Why this was the correct fix

There were only two realistic options:

1. rewrite verification logic outside DCAP
2. keep DCAP and fix the identity mismatch at the right boundary

The second option is better for this repository because:

- it preserves `tee_qv_get_collateral()`
- it preserves `tdx_qv_verify_quote()`
- it keeps the behavioral surface aligned with DCAP
- it limits the custom logic to the one place where the stock assumptions are false

## Short summary

What made the full DCAP path work was not changing the quote to become `type 5`.

The quote was already `type 5`.

The real fix was:

- detect `QEIDENTITY_MISMATCH`
- synthesize a local `TDQE identity` from the quote's `qe_report`
- retry `tdx_qv_verify_quote()` with that identity
- add a narrow verifier-side gate to accept that explicit local identity

That is the change that turned the `ML-DSA-65` hardware flow from:

- real quote + local fallback

into:

- real quote + collateral fetch + successful `tdx_qv_verify_quote()`
